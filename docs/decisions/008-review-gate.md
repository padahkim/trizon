# 008. 머지하기 전에 PreToolUse 훅으로 PR 리뷰가 정리됐는지 확인한다

- 상태: 채택 (2026-10-11)
- 관련: 007(같은 구조의 Stop 훅), 동작은 루트 `AGENTS.md`의 "PR 리뷰와 머지"와 `scripts/review-gate.ts`

## 맥락

- PR을 열면 몇 분 안에 Codex 봇(`chatgpt-codex-connector`)이 인라인 리뷰를 단다. 이 리포에서는 사실상 유일한 리뷰다.
- 그런데 리뷰 대응과 머지 전 확인을 매번 사람이 부탁했다. 2026-09-27~10-10 세션 기록에서 "코덱스 리뷰 대응해줘", "리뷰 대응하고 머지한 건가?" 같은 요청이 4개 세션에서 6번 넘게 나왔다.
- 부탁이 빠지면 지적이 조용히 묻혔다.
  - PR #1은 리뷰가 달리고 3분 뒤에 머지돼 지적 2건을 대응하지 못했다.
  - PR #3은 대응 커밋 3개를 로컬에서만 만들고 push하기 전에 머지됐다.
  - 둘 다 PR #5로 뒤늦게 모아 올렸다.
- 머지 전에 확인할 것은 회사 PC Claude의 메모리에만 있었다. 집 PC의 Codex는 몰랐다.
- 지적을 판단하고 고치고 답글을 다는 일은 부탁하면 에이전트가 해냈다. 빠진 것은 "머지 전에 확인한다" 하나였다.

## 결정

- `gh pr merge`가 실행되기 직전에 도는 PreToolUse(Bash) 훅으로 막는다. 로직은 도구 중립인 `scripts/review-gate.ts` 하나에 두고, `.claude/settings.json`과 `.codex/hooks.json`은 이 스크립트를 가리키기만 한다(007과 같은 구조).
- 다음 중 하나라도 해당하면 exit 2로 막고, 이유와 스레드 URL을 stderr로 에이전트에게 돌려준다.
  1. Codex 리뷰가 아직 없거나 끝나지 않았다. 요약 코멘트(`<!-- codex-pull-request-review-summary -->`)의 상태를 보고, 요약 코멘트가 생기기 전의 PR(#1~#5)은 리뷰 본문을 본다.
  2. Codex 리뷰가 실패했다.
  3. resolve되지도 않았고 답글도 없는 리뷰 스레드가 있다. Codex뿐 아니라 Copilot·사람 리뷰도 같게 본다.
  4. 로컬 PR 브랜치에 PR head에 없는 커밋이 있다. `--repo`로 다른 리포의 PR을 가리키면 로컬 브랜치와 비교할 수 없어 보지 않는다. `--repo`로 이 리포(origin)를 적은 경우는 비교한다.
- 자동 머지를 취소하는 `gh pr merge --disable-auto`는 머지가 아니라서 막지 않는다. 리뷰가 덜 됐을 때야말로 취소해야 하기 때문이다.
- gh가 "그런 PR이 없다"고 답할 때만 통과시킨다(번호 오타, PR이 없는 브랜치 등). 진짜 머지 명령이면 gh가 같은 이유로 실패한다. 인증 실패·rate limit·일시 오류처럼 조회만 실패하고 머지는 성공할 수 있는 경우와, PR은 찾았는데 리뷰를 읽지 못한 경우는 막는다.
- 사용자가 이 상태로 머지하라고 명시했을 때만 명령 앞에 `TRIZON_SKIP_REVIEW_GATE=1`을 붙여 건너뛴다. 예: PR #6처럼 리뷰 실패를 알고도 머지하기로 한 경우.
  - 건너뛰기는 그 `gh pr merge` 앞에 환경변수로 붙인 것만 인정한다. 같은 명령 줄의 다른 곳(예: `echo`)에 문자열이 있어도, 다른 머지에 붙어 있어도 건너뛰지 않는다.
- 같은 스크립트를 `npm run review:status -- <PR>`로 사람도 쓴다.
- 판정 로직은 가짜 조회를 넣어 `npm test`에서 네트워크 없이 검사한다(005). 이를 위해 테스트 범위를 `scripts/`까지 넓혔다.

지난 PR #1~#7에 돌려 보니 #3에서 로컬 브랜치에 남은 커밋 3개를 잡았다. 당시 빠진 대응 커밋이다. #6은 리뷰 실패로, Codex 리뷰가 달리지 않은 #2는 리뷰 없음으로 막힌다.

## 버린 대안

- **대응 절차를 Skill로 묶기(`.claude/skills/`):** 에이전트가 스킬을 부를 때만 돈다. 머지를 서두를 때 확인이 빠지는 문제는 그대로다. 도구 전용 폴더라 Codex에도 닿지 않는다(006).
- **`AGENTS.md` 지시나 에이전트 메모리만 두기:** 지금까지의 상태다. 강제력이 없고, 메모리는 한 PC에만 있다.
- **GitHub 브랜치 보호의 "Require conversation resolution before merging":**
  - 사람이 GitHub 화면에서 머지할 때도 걸린다는 장점이 있다.
  - 하지만 스레드를 resolve해야만 통과한다. 답글로 대응하던 관례를 바꿔야 한다.
  - 리뷰가 아직 안 왔거나 실패한 경우, push 안 한 커밋은 잡지 못한다.
  - 설정이 리포 밖에 있어 다른 PC나 에이전트가 볼 수 없다.
- **CI(GitHub Actions) 필수 체크:** Codex 리뷰는 PR을 연 뒤 비동기로 달려서, 리뷰가 달린 뒤 체크를 다시 돌릴 트리거가 따로 필요하다. 로컬에만 있는 커밋은 CI가 볼 수 없다.

## 감수하는 것

- 모든 Bash 호출마다 node가 한 번 뜬다. 머지 명령이 아니면 조회 없이 끝나며, 약 50~80ms가 더 든다.
- 명령은 셸처럼 완전히 해석하지 않는다. 따옴표만 처리해서 따옴표 밖의 `;` `&` `|` 괄호 줄바꿈마다 끊고, 첫 단어가 `gh`인 `gh pr merge`를 모두 본다. 하나만 보면 `gh pr merge 8 && gh pr merge 9`의 9가 검사 없이 머지된다.
  - heredoc 커밋 메시지의 한 줄이 `gh pr merge`로 시작하면 걸릴 수 있다. 그때 PR을 찾지 못하면 통과한다.
  - `bash -c "…"`처럼 따옴표 안에 넣은 명령, `gh api .../merge`, MCP 도구로 머지하면 걸리지 않는다.
- 사람이 GitHub 화면에서 머지하면 걸리지 않는다.
- 건너뛰기는 에이전트가 "사용자가 명시했을 때만"이라는 지시를 지킨다는 전제에 기댄다.
- Codex 요약 코멘트의 형식(표, `Completed`·`Failed` 문자열)에 기댄다. 진행 중일 때의 문자열은 관측하지 못해서, 둘 다 아니면 진행 중으로 본다.
- 리뷰 스레드는 PR마다 100개까지만 본다.
- Antigravity에는 훅을 걸지 않았다. 이유는 007과 같다.

## 다시 볼 조건

- Codex 요약 코멘트나 리뷰 형식이 바뀌어 판정이 틀릴 때.
- 사람이 GitHub 화면에서 머지하다가 리뷰를 놓치는 일이 생길 때. 브랜치 보호를 다시 검토한다.
- Copilot 등 다른 리뷰어를 상시로 붙일 때.
