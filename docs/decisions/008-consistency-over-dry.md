# 008. 같은 일은 한 가지 방법으로 하고, 판단 기준은 Consistency over DRY로 한다

- 상태: 채택 (2026-10-11)
- 관련: 006(도구 중립 지침), 007(Stop 훅 검사), 표준과 폐기 목록은 `docs/golden-rules.md`

## 맥락

- 이 리포는 코딩 에이전트 여러 개로 작업한다(006). 에이전트는 근처 코드를 보고 따라 쓴다. 같은 일을 하는 방법이 둘이면 절반 확률로 다른 쪽을 고르고, 방법이 셋이 되면서 어긋남이 곱으로 늘어난다.
- 2026-10-11 `development`를 감사하니 경쟁하는 중복 패턴이 app/에서 12건, lib/·scripts/에서 12건 나왔다. 예를 들면 다음과 같다.
  - 날짜·시각 표시 함수가 다섯 벌이고, 같은 시각이 화면마다 다르게 보인다.
  - 필드까지 같은 파일 오류 클래스가 두 벌이다.
  - 티커 정규식 복사본이 세 개다.
  - 쓰기 액션마다 revalidate하는 화면이 다르다. 계좌를 추가해도 /sbi에 바로 반영되지 않는다.
  - 폼 숫자를 읽는 규칙이 세 벌이다. 그중 하나는 "1,000"을 읽지 못한다.
- `docs/architecture.md`와 폴더별 `AGENTS.md`는 "지금 어떻게 동작하나"를 적는다. "새 코드는 무엇을 쓰고 무엇을 따라 쓰지 말라"는 목록은 어디에도 없었다.
- DRY를 끝까지 밀면 반대 문제가 생긴다. 옵션으로 갈라지는 공통 추상화가 생기고, 에이전트는 정의를 따라가야 동작을 안다. 반대로 모든 것을 인라인으로 반복하면, 통화별 자릿수처럼 틀리면 돈이 틀리는 규칙이 복사본마다 어긋난다.

## 결정

- **하나로 고정한다:** 경쟁하는 패턴을 찾으면 표준을 하나로 정한다. 나머지는 같은 PR에서 바꾸고, 못 바꾸면 `docs/golden-rules.md`의 "폐기된 패턴"에 올린다. 이 목록은 줄기만 해야 한다.
- **판단 기준은 Consistency over DRY다.** DRY·SOLID를 버리는 것이 아니라 언제 쓰는지의 기준을 바꾼다. 기준 질문은 "다음 에이전트가 근처 코드를 복사해도 맞는가"다.
  - 틀리면 돈이나 데이터가 틀리는 규칙은 한 곳에 모은다. 금액 표시, 통화 환산, 종목코드, 스키마, 저장 파일, revalidate 대상이 여기에 해당한다.
  - 한 줄 관용구·테스트 헬퍼·화면 조립 코드는 글자까지 같은 모양으로 반복한다.
  - 한 번만 쓰는 함수나 옵션으로 갈라지는 범용 래퍼는 만들지 않는다.
- **표준은 한 곳에 둔다:** 표준과 폐기 목록은 `docs/golden-rules.md` 하나에 둔다. 루트 `AGENTS.md`에서 `@`로 불러 항상 로드한다. RAG로 찾기 쉽게 frontmatter(`type`·`tags`·`last_reviewed`)를 달고, 한 문단에 한 주제를 쓰며, 검색어가 본문에 나오게 쓴다.
- **강제는 테스트가 한다:** 기계로 검사할 수 있는 규칙은 테스트로 만들어 `npm run check`가 잡게 한다. 그러면 007의 Stop 훅이 에이전트를 돌려보낸다. 아직 고치지 못한 곳은 테스트 안의 예외 목록 한 곳에만 두고, 고치면 지우게 한다.
- **로그는 JSON line이다:** 서버의 진단 로그는 `console.error(JSON.stringify({ ts, event, … }))` 한 줄로 쓴다. lib/는 로그를 찍지 않고 결과의 `warnings`로 돌려준다. 에이전트가 `jq`로 골라 읽고 자기 작업을 확인할 수 있게 하려는 것이다.
- **의존성은 묻고 기록한다:** 새 npm 의존성은 추가하기 전에 사용자에게 묻고, 채택하면 docs/decisions/에 기록한다.

## 버린 대안

- **DRY를 엄격하게:** 저장소마다 다른 규칙(파일이 없을 때, 버전)을 옵션으로 받는 공통 reader 같은 것이 생긴다. 읽는 쪽이 정의와 옵션 조합을 따라가야 한다.
- **금액 포맷까지 인라인 반복:** KRW·JPY는 소수 0자리, USD는 2자리이고 억·만 단위도 있다. 복사본마다 어긋나면 화면의 금액이 틀린다.
- **`handlers/`·`services/`·`repositories/` 표준 구조로 재구성:** lib/는 이미 도메인 폴더와 역할별 파일 이름(`parse.ts`·`service.ts`·`store.ts`)으로 일관돼 있다. 옮겨서 얻는 것보다 히스토리와 링크를 잃는 비용이 크다.
- **`CLAUDE.md`에서 `GOLDEN_RULES.md`를 참조:** 006에 어긋난다. `CLAUDE.md`가 있으면 Claude Code가 `AGENTS.md`를 읽지 않는다.
- **루트에 `GOLDEN_RULES.md`:** 문서는 `docs/`에 둔다는 규칙(루트 `AGENTS.md`의 "지침 파일 관리")에 어긋난다.
- **문서만 두기:** 007과 같은 이유로 강제력이 없다.
- **logger 모듈:** 지금 진단 로그를 쓰는 곳이 한 곳뿐이라, 모듈을 만들면 한 번만 쓰는 추상화가 된다.

## 감수하는 것

- 폐기 목록이 남아 있는 동안은 두 방법이 공존한다. 목록이 "따라 쓰지 말라"는 신호를 대신한다.
- 규칙 검사는 소스 문자열을 보는 방식이라 오탐이 날 수 있고, 마음먹으면 우회할 수 있다.
- "모을지, 반복할지"는 여전히 판단이 필요하다. 기준 질문으로 좁힐 뿐이다.

## 다시 볼 조건

- 폐기 목록이 줄지 않고 늘기만 할 때. 감사(golden-rules 7절) 주기나 PR 범위를 다시 본다.
- 규칙 검사 테스트의 오탐이 잦을 때.
- 로그를 모아 쿼리하는 도구(LogQL 등)를 붙일 때. 그때 logger 모듈과 필드 규칙을 다시 정한다.
